# Stampies server-authoritative loyalty ledger

**Scope:** merchant locations, configurable programs, anonymous Wallet customer
enrolment, atomic stamps, reward redemption and immutable audit history.
This is production-oriented backend code, not another demo dataset. It is
deliberately isolated from Expo, which still shows sample data on main.

## Dependencies

Requires the merchant identity schema and verified OIDC token/membership
adapters from **PR #5**, and the fail-closed Wallet ingestion boundary from
**PR #3**. Keep this change on its own branch until those dependencies are
reviewed. It does not modify the other agents' files.

Migration order on a test/staging database:
1. server/auth/postgres/001-merchant-identities.sql (from PR #5)
2. server/loyalty/postgres/001-loyalty-ledger.sql
3. server/loyalty/postgres/provision-loyalty-runtime.sql

The migration creates zero merchants, programs, customers, balances, staff PINs
or fake events. Use a dedicated restricted Postgres service principal
associated with the NOLOGIN loyalty role. The runtime has only the SELECT,
INSERT, narrow UPDATE and enrolment-grant DELETE privileges it requires.
It must not run schema migrations and must not be reachable from client
devices. Real provisioning of merchant and active owner accounts must be done
through a separate privileged onboarding service.

## Server API composition (trusted host only)

~~~js
import {createPostgresLoyaltyLedger} from './server/loyalty/postgres/ledger.mjs';
import {createOidcAccessTokenVerifier} from './server/auth/oidc-jwt.mjs';
import {createPostgresMerchantMembershipStore} from './server/auth/postgres/membership-store.mjs';

const verifyAccessToken = createOidcAccessTokenVerifier({
  issuer: configuredIssuer, audience: apiAudience, jwksUri: configuredJwksUri,
});
const {lookupMembership} = createPostgresMerchantMembershipStore({
  pool: restrictedIdentityPool,
});
const loyalty = createPostgresLoyaltyLedger({
  pool: restrictedLoyaltyPool, verifyAccessToken, lookupMembership,
});
~~~

These are injection points, not a production server: host configuration,
identity-provider connection, session management, rate limiting, endpoint
routing, telemetry and durable deployment are separately required. Never
replace the verification callback with JWT decoding or an allow-all stub.

## Operations

- createLocation: active merchant owner/admin creates an actual branch.
- createProgram: owner/admin sets reward text, stamp target (1 to 100), daily
  limit (1 to 20), cooldown seconds (0 to 86400), and IANA timezone.
  Published program configuration is not mutated mid-card; add a versioned
  program update flow before exposing editing in production.
- createEnrollmentGrant: authenticated merchant staff creates a five-minute,
  256-bit, one-time token; only its SHA-256 digest is retained in Postgres.
- enrollCustomer: a customer can join without login using that one-time grant
  and the public program code. A fresh opaque pass ID and zero-balance
  membership are generated by the server. No personal data is required.
- issueStamp: verified active staff/member, same merchant, active location
  and program; row-level pass lock before every check; idempotent transaction
  key, timezone-aware daily limit, cooldown and configurable stamp target.
- redeemReward: same authorisation and row lock; checks the live balance
  against the configured target; records an immutable redemption event and
  resets balance in the SAME database transaction.
- getMerchantPass: authenticated merchant-scoped read of balances and
  aggregate redemption counters, never a hardcoded demo number.

Every event records the actor identity, merchant, branch, pass, local day,
request digest, previous/next balance and server timestamp. The database
uses composite foreign keys for tenant isolation. Repeated requests return
the original result; the same idempotency key used for a different operation
or location is rejected. Simultaneous stamps for one pass serialize using
Postgres SELECT FOR UPDATE. Duplicate processing cannot silently inflate
the balance.

The server controls identity, program rules, time and balances. Neither a
Wallet barcode, client request timestamp, QR graphic nor a 4-digit PIN is
trusted to grant a stamp. Event IDs are server-generated.

## Still required before production release

- Merge PR #5, connect a real OIDC provider and implement secure merchant
  onboarding, tenant ownership, staff invitations and revocation.
- Build authenticated HTTP API route handlers with validated request bodies,
  CSRF/CORS policy where applicable, abuse limits and careful error mapping.
- Connect real customer enrolment to a live, signed Apple/Google pass issuer.
  The existing Wallet server's stamp ledger MUST NOT be run as a second
  independent authority. Use this ledger as the single balance authority,
  project committed events into the Wallet update system, and retire the
  duplicate intake path after end-to-end migration tests.
- Replace all demo data/UI and self-stamping flows in the Expo app with the
  real merchant/customer API, pending/error states and server-confirmed
  results. Never show "Added to Wallet", "Stamp earned" or "Reward redeemed"
  without the corresponding verified result.
- Add DB integration tests against an isolated disposable Postgres,
  including actual concurrent transactions, migration/grant validation,
  clock/DST transitions, request replay, rollback and crash recovery.
- Add merchant billing, role-scoped dashboards, consent-driven campaigns,
  customer privacy controls, reporting, multi-location administration,
  fraud monitoring, backups and operational tools.
- Verify physical iOS/Android Wallet issuance, update and redemption.

## Verification

Run: node --test tests/loyalty-ledger.test.mjs

Fixture tests cover valid and repeated stamps, idempotency conflicts,
configurable rewards, redemption, tenant authorisation, daily limits,
timezone boundaries, staff revocation and one-time anonymous enrolment.
The GitHub workflow Stampies Loyalty Ledger runs these on relevant PRs.
These tests use a deterministic test DB adapter, NOT a production database
or a physical phone. Do not merge without passing CI and independent review.
